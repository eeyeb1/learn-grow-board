- Centralize page-entry scroll handling inside the router so links and navigation buttons share consistent behavior while job-filter updates retain position.
- Verified hours are computed only in database functions (get_my_hours_summary, get_public_profile) from approved hour_entries; a trigger forces new/edited seeker entries to pending so the client can never self-verify.
- Public seeker profiles are read only via the get_public_profile RPC, which returns opt-in fields only; never expose public_profiles or profiles rows to anon directly.
- Placements are created only by a trigger when an employer accepts an application; status changes and detail edits go through audited SECURITY DEFINER RPCs (placement_action, update_placement_details) that write placement_events — there are no client write policies on placements.
- Certificates are issued only by the issue_certificate RPC, which snapshots name, dates, approved hours and confirmed skills from server records; the PDF is rendered client-side from that row only, and public checks go through verify_certificate, which honours the seeker's privacy flags. Why: totals must never come from client input.
- Portfolio files live in the private `portfolio` bucket and are only ever served through the `portfolio-file` edge function, which checks publication/ownership/employer access and the file's magic bytes; public data comes from get_public_profile and never includes storage paths. Removal requests and moderation go through SECURITY DEFINER RPCs. Why: private file URLs must never leak.
- Seekers' AI CV writer runs in the cv-writer edge function using the caller's own session (RLS) to load only completed placements, approved hours, verified skills and chosen diary entries; contact details are redacted and no name/email is sent. Why: AI output must be grounded in server records and private data must not reach the model.
- Seeker recommendations are rule-based and explainable (src/lib/recommendations.ts, tested with bun test): only active, unexpired listings; inputs limited to chosen preferences and feedback, never age/minor/education/personal data. Why: rankings must be auditable and non-discriminatory.
- Seeker notifications are created only by SECURITY DEFINER triggers/RPCs via `_notify` (not client-executable), deduplicated by UNIQUE(user_id, dedupe_key) and filtered by notification_preferences; clients may only change read_at. Previews are generic; details render only from the user's own RLS-scoped rows. Why: no forged or duplicate notifications, no sensitive details in previews.
- Employer presentation uses the existing auth identity; company access is read through get_company_access and company-scoped permissions come from protected verification/membership records, never profiles.user_type or registration metadata. Why: seeker workspace switching must not create privileges or competing identities.
- Company domain eligibility is separate from membership; jobs enforce verified administrator publication and private owner drafts, while placement access requires explicit company management permission. Trusted company reviews and initial administrator appointments are service-side only. Why: verified email alone cannot represent a company or disclose seeker records.
