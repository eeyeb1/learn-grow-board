- Page-entry scroll handling lives in the router; job-filter updates keep position.
- Company page settings are private and admin-edited through save_company_page; public reads use get_public_company's whitelist and completed/approved impact with a five-participant privacy threshold. Logos use private storage, PNG re-encoding and publication-scoped signed reads. Why: no operational or small-cohort leaks.
- Verified hours are computed only in database functions (get_my_hours_summary, get_public_profile) from approved hour_entries; a trigger forces new/edited seeker entries to pending so the client can never self-verify.
- Public seeker profiles are read only via the get_public_profile RPC, which returns opt-in fields only; never expose public_profiles or profiles rows to anon directly.
- Placements are trigger-created on acceptance (one per application) and changed only via audited RPCs (placement_action, update_placement_details/onboarding, assign_placement_supervisor for Supervisor-scope members); activation needs supervisor, details, induction checklist and seeker confirmation.
- Assigned supervisors/company admins complete after hour review; issue_certificate runs atomically. Snapshots change only via audited revoke/reissue; verification respects privacy. Why: trusted proof.
- Portfolio files stay in the private `portfolio` bucket, served only via the `portfolio-file` function; removals use SECURITY DEFINER RPCs. Why: no URL leaks.
- The cv-writer function uses the caller's RLS session to load only completed placements, approved hours, verified skills and chosen diary entries, redacting contacts. Why: grounded output, no private data to the model.
- Seeker recommendations are rule-based (src/lib/recommendations.ts): active, unexpired listings; chosen preferences/feedback only, never age/minor/education/personal data. Why: fair, auditable.
- Seeker notifications are created only by SECURITY DEFINER triggers/RPCs via `_notify` (not client-executable), deduplicated by UNIQUE(user_id, dedupe_key) and filtered by notification_preferences; clients may only change read_at. Previews are generic; details render only from the user's own RLS-scoped rows. Why: no forged/duplicate notifications or sensitive previews.
- Employer presentation uses the existing auth identity; company access is read through get_company_access and company-scoped permissions come from protected verification/membership records, never profiles.user_type or registration metadata. Why: seeker workspace switching must not create privileges or competing identities.
- Company operational access uses protected staff scopes and explicit resource assignments; legacy manage_placements is never authority. Private drafts become company-reviewable only on submission; public manager edits return to draft and administrator approval is version-bound. Permission changes are append-only audited. Why: broad membership, mailbox proof or editing rights must never reveal unrelated seeker records or publish without company approval.
- Employee work addresses are separate private identities: service-issued hashed challenges require account-bound atomic confirmation, while company_can_draft resolves exact approved domains and company_permission binds employee membership to its approved work address. Address changes pause employee permissions. Why: mailbox proof is never authority.
- Work-email delivery uses the shared app-email sender, a registered template and trusted HTTPS origin; fails closed until configured. Why: tokens never reach clients.
- Company verification uses private submissions and append-only administrator reviews; the protected review RPC atomically resolves canonical companies, appoints members, approves eligible domains and notifies applicants. Why: evidence must never enter public profiles, and registration cannot transfer an established company identity.
- Company notices bypass seeker notification preferences.
- Company staff invitations are bound to an exact approved-domain work email and accepted only by the account that verified it (no bearer token); admin promotion and zero-admin platform recovery go through checked, audited RPCs. Why: no transferable invites or self-granted admin.
- Guided opportunities reuse `jobs` (category + whitelisted `opportunity_details` jsonb); `check_opportunity` validates loosely on draft saves and strictly on review requests/publication, and `job_versions` is trigger-written only. Why: autosave must accept partial drafts while nothing incomplete or mis-categorised (unpaid productive work, missing pay/supervision) can reach review.
- `jobs.status` (`active` = Published, only public state) changes only via RPCs setting `app.job_transition`; material edits after approval revert to draft; reviews bind to publication_revision/approved_snapshot. Why: no unapproved revision goes live.
- Self-authored company-admin approvals are allowed only for categories where requires_second_authoriser() is false, are flagged self_authored_approval by trigger and always go to platform review; the Approval Centre reads via list_company_approval_requests (admin-only). Why: no sole authority on risky listings.
- Listing management (pause/resume/close/archive/duplicate) goes through set_job_listing_state/duplicate_job_as_draft gated by can_manage_listing; resume needs the current revision's approved snapshot; guard_application_open blocks applications to non-published/expired real listings. Why: no unapproved version goes live and history is never deleted.
- Application stages change only via set_application_status/withdraw_application (trigger blocks direct writes; application_events append-only); employers read via list_company_applications (no contacts/diary/private portfolio). Why: one shared record, no leaks or double acceptances.
- Hours/feedback require assigned supervisors; immutable events retain revisions. Skill edits reset consent; hidden/revoked skills stay nonpublic. Why: seeker ownership.
- Messaging: one conversation per application, RPC-only; staff access reuses application/placement authority; guardians read-only; safeguarded seekers need an approved guardian. Why: no contact outside authorised relationships.
