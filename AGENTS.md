- Centralize page-entry scroll handling inside the router so links and navigation buttons share consistent behavior while job-filter updates retain position.
- Company page settings are private and admin-edited through save_company_page; public reads use get_public_company's whitelist and completed/approved impact with a five-participant privacy threshold. Logos use private storage, PNG re-encoding and publication-scoped signed reads. Why: optional publication must not expose company operational records or small-cohort seeker data.
- Verified hours are computed only in database functions (get_my_hours_summary, get_public_profile) from approved hour_entries; a trigger forces new/edited seeker entries to pending so the client can never self-verify.
- Public seeker profiles are read only via the get_public_profile RPC, which returns opt-in fields only; never expose public_profiles or profiles rows to anon directly.
- Placements are created only by a trigger when an employer accepts an application; status changes and detail edits go through audited SECURITY DEFINER RPCs (placement_action, update_placement_details) that write placement_events — there are no client write policies on placements.
- Certificates are issued only by the issue_certificate RPC, which snapshots name, dates, approved hours and confirmed skills from server records; the PDF is rendered client-side from that row only, and public checks go through verify_certificate, which honours the seeker's privacy flags. Why: totals must never come from client input.
- Portfolio files live in the private `portfolio` bucket and are only ever served through the `portfolio-file` edge function, which checks publication/ownership/employer access and the file's magic bytes; public data comes from get_public_profile and never includes storage paths. Removal requests and moderation go through SECURITY DEFINER RPCs. Why: private file URLs must never leak.
- Seekers' AI CV writer runs in the cv-writer edge function using the caller's own session (RLS) to load only completed placements, approved hours, verified skills and chosen diary entries; contact details are redacted and no name/email is sent. Why: AI output must be grounded in server records and private data must not reach the model.
- Seeker recommendations are rule-based and explainable (src/lib/recommendations.ts, tested with bun test): only active, unexpired listings; inputs limited to chosen preferences and feedback, never age/minor/education/personal data. Why: rankings must be auditable and non-discriminatory.
- Seeker notifications are created only by SECURITY DEFINER triggers/RPCs via `_notify` (not client-executable), deduplicated by UNIQUE(user_id, dedupe_key) and filtered by notification_preferences; clients may only change read_at. Previews are generic; details render only from the user's own RLS-scoped rows. Why: no forged or duplicate notifications, no sensitive details in previews.
- Employer presentation uses the existing auth identity; company access is read through get_company_access and company-scoped permissions come from protected verification/membership records, never profiles.user_type or registration metadata. Why: seeker workspace switching must not create privileges or competing identities.
- Company operational access uses protected staff scopes and explicit resource assignments; legacy manage_placements is never authority. Private drafts become company-reviewable only on submission; public manager edits return to draft and administrator approval is version-bound. Permission changes are append-only audited. Why: broad membership, mailbox proof or editing rights must never reveal unrelated seeker records or publish without company approval.
- Employee work addresses are separate private identities: service-issued hashed challenges require account-bound atomic confirmation, while company_can_draft resolves exact approved domains and company_permission binds employee membership to its approved work address. Address changes pause employee permissions. Why: mailbox proof must not become company authority or survive an address change.
- Work-email delivery uses the shared app-email sender with a registered employee-work-email template and trusted HTTPS app origin; fail closed until the sender is configured. Why: no raw token may reach a client or an untrusted redirect and unconfigured delivery cannot produce verification.
- Company verification uses private submissions and append-only administrator reviews; the protected review RPC atomically resolves canonical companies, appoints members, approves eligible domains and notifies applicants. Why: evidence must never enter public profiles, and registration cannot transfer an established company identity.
- Company notification events use the existing recipient-scoped notification system as mandatory service updates, separate from seeker category preferences. Why: company applicants need approval notices without changing seeker notification choices.
- Company staff invitations are bound to an exact approved-domain work email and accepted only by the account that verified it (no bearer token); admin promotion and zero-admin platform recovery go through checked, audited RPCs. Why: invitations must be non-transferable and admin authority must never be self-granted.
- Guided opportunities reuse `jobs` (category + whitelisted `opportunity_details` jsonb); `check_opportunity` validates loosely on draft saves and strictly on review requests/publication, and `job_versions` is trigger-written only. Why: autosave must accept partial drafts while nothing incomplete or mis-categorised (unpaid productive work, missing pay/supervision) can reach review.
- Opportunity lifecycle states live in `jobs.status` (`active` = Published, the only public state) and change only through SECURITY DEFINER RPCs that set `app.job_transition`; material edits (job_material) after approval revert to draft, reviews bind to publication_revision and approved_snapshot, and job_review_events is append-only. Why: no one may bypass company/platform approval or publish an unapproved revision.
